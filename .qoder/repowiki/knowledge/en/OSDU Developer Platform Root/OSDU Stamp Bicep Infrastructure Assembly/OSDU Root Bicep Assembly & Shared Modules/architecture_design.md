Two top-level entry points define the deployment surface: `main.bicep` provisions a full OSDU stamp (identity, Log Analytics, App Insights, Redis, AKS cluster via `modules/blade_cluster.bicep`, optional VNet via `modules/blade_network.bicep`, ACR, Key Vault with secrets, Cosmos DB, Storage Account, Flux extension, partition blades, and configuration blade), while `main-minimal.bicep` deploys a minimal subset (identity, Log Analytics, App Insights, Key Vault, Storage, Static Web App) for quick bootstrap. Both files target `resourceGroup` scope and compose resources through two patterns: (1) public Azure Verified Modules (AVM) referenced by registry path (`br/public:avm/...`) for foundational services, and (2) local reusable modules under `bicep/modules/` organized as *blades* (`blade_cluster`, `blade_network`, `blade_partition`, `blade_configuration`) and domain-specific infra (`storage-account`, `cosmos-db`, `managed-cluster`, `flux-configuration`, `flux-extension`, `private-endpoint`, `app-configuration`, `aks-config-map`, `aks-run-command`, `script-share-*`, `software-upload`, `deploy-scripts`). Dependency direction is strictly inward: the root assembly declares module instances with explicit `dependsOn` chains driven by feature flags (e.g., `enableVnetInjection` gates `networkBlade`; `clusterSoftware.enable` gates software upload). Cross-cutting concerns are factored into sibling files at the root of `modules/` (`keyvault_secrets.bicep`, `federated_identity.bicep`, `cosmosdb-sql-role-assignment.bicep`, `network_acl_*`), which are consumed by blade modules rather than directly from the root. Each sub-module follows a consistent layout with `main.bicep`, generated `main.json`, `version.json`, and optional `.bicep/` nested helpers plus `test/` suites, enabling independent unit/e2e validation.
