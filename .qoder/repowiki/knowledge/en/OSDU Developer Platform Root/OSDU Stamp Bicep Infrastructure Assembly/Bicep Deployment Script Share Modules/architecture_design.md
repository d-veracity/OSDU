Each subdirectory is a self-contained Bicep module following the same pattern: an `main.bicep` declares parameters (storage account, managed identity, share/container name, source URL), references existing `Microsoft.Storage/storageAccounts` and `Microsoft.ManagedIdentity/userAssignedIdentities` resources, conditionally assigns an RBAC role (`Storage File Data SMB Share Contributor` or `Storage Blob Data Owner`) to the identity on the storage scope, and then instantiates the public Bicep module `br/public:avm/res/resources/deployment-script:0.5.1` with `kind: 'AzureCLI'`, `runOnce: true`, and `scriptContent: loadTextContent('script.sh')`. The embedded `script.sh` runs inside the ephemeral Azure CLI container, waits for RBAC propagation via `initialDelay`, installs Alpine packages (`curl`, `zip`, `jq`, etc.), downloads content from `URL`, optionally extracts archives, performs in-place transformations, and uploads via `az storage file upload`/`upload-batch` or `az storage blob upload-batch` using `--auth-mode login` so the managed identity authenticates. Three specialized variants exist: `script-share-upload` uploads single files or tar.gz archives to a file share; `script-share-csvdag` additionally parses a JSON `SEARCH_AND_REPLACE` list to perform find/replace substitutions on a Python DAG file before zipping and uploading; `software-upload` downloads a repo archive, does a sed-based `GitRepository`→`Bucket` kind rewrite under a target directory, and uploads the result to a blob container. A sibling `deploy-scripts/` folder holds standalone shell helpers (`blob_upload.sh`, `software-upload.sh`) plus a `Legal_COO.json` artifact used outside the deployment-script lifecycle.
