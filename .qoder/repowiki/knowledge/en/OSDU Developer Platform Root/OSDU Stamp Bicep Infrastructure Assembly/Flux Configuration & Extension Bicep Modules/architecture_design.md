Two sibling Bicep modules, each published as an Azure Verified Module (AVM) with its own `main.bicep`, compiled `main.json`, and `version.json` declaring version `0.3` and publishing only `./main.json`. The `flux-configuration` module declares parameters for source kind (`Bucket`, `GitRepository`, `AzureBlob`), kustomizations, scope (`cluster`/`namespace`), and protected settings, then creates an existing reference to the target `Microsoft.ContainerService/managedClusters` resource and deploys a `Microsoft.KubernetesConfiguration/fluxConfigurations@2025-04-01` scoped to it. The `flux-extension` module deploys a `Microsoft.KubernetesConfiguration/extensions@2024-11-01` of type `microsoft.flux` with optional release train/version/target namespace, and then iterates over an input `fluxConfigurations` array to instantiate the `flux-configuration` module via a nested module loop, explicitly depending on the extension so the Flux extension is installed before any configurations are reconciled. Both modules include an optional telemetry deployment (`avmTelemetry`) gated by `enableTelemetry`. Tests under `tests/e2e/{defaults,max,waf-aligned}` follow the AVM convention: each scenario defines a `dependencies.bicep` that provisions an AKS cluster and a `main.test.bicep` that targets subscription scope, instantiates the module twice with `['init', 'idem']` iterations via `@batchSize(1)` to verify idempotency, and passes minimal or full parameter sets accordingly.
