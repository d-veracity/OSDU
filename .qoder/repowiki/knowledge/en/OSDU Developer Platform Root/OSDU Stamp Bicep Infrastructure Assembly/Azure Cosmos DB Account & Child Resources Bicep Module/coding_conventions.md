- Child resources are created via Bicep `module` blocks inside `for` loops keyed by input arrays (e.g. `sqlDatabases`, `gremlinDatabases`, `roleAssignments`), each iteration receiving a unique `name` derived from `deployment().name` plus an index or identifier.
- Optional capabilities are guarded by conditional expressions on string/object parameters (e.g. `if (!empty(keyVaultName))`, `if (enablePrivateLink)`, `if (isSystemPartition)`) rather than separate files, keeping feature toggles declarative at the call site.
- Throughput configuration follows a mutually exclusive pattern: `throughput == -1` selects autoscale (`maxThroughput`) while any other value sets explicit RU/s, applied consistently across SQL and Gremlin database sub-modules.
- Sub-modules declare their parent resource as an `existing` reference (e.g. `databaseAccount existing { name: databaseAccountName }`) instead of re-declaring it, enforcing a single source of truth for the account lifecycle.
- Built-in role names are resolved via a local `builtInRoleNames` map that maps friendly names to `subscriptionResourceId('Microsoft.Authorization/roleDefinitions', <guid>)`, falling back to the raw `roleDefinitionIdOrName` when not found.
- Secret values written to Key Vault are marked with `@secure()` on the parameter and retrieved from the deployed account via `listKeys()` / `listConnectionStrings()` so sensitive data never appears in template text.
