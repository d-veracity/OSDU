Three sibling Bicep modules under `bicep/modules/` form a cohesive AKS provisioning surface:
- `managed-cluster/main.bicep` is the top-level module that declares the `Microsoft.ContainerService/managedClusters` resource, composes sub-modules for `agent-pool` (one per pool via a Bicep array loop) and `maintenance-configurations`, attaches optional extensions (Flux via `br/public:avm/res/kubernetes-configuration/extension`), and emits role assignments, diagnostic settings, locks, DNS zone contributor roles, and identity outputs. It delegates network, addon, autoscaler, security, storage, and monitoring profiles into the single managed cluster resource.
- `managed-cluster/agent-pool/main.bicep` and `managed-cluster/maintenance-configurations/main.bicep` are leaf child modules referenced by the parent via `module ... 'path' = { params: ... }`, each declaring an `existing` reference to the parent cluster and creating a child resource (`managedClusters/agentPools`, `managedClusters/maintenanceConfigurations`).
- `aks-config-map/main.bicep` and `aks-run-command/main.bicep` follow an identical pattern: they declare an `existing` AKS reference, optionally create or reuse a user-assigned managed identity, assign Contributor + RBAC Reader roles to it, then spin up one or more `Microsoft.Resources/deploymentScripts@2023-08-01` of kind `AzureCLI` whose `scriptContent` is loaded from a sibling shell script (`aks-configmap-command.sh`, `aks-run-command.sh`) via `loadTextContent`. The run-command variant uses `@batchSize(1)` over an input `commands` array to emit one deployment script per command.
- Tests live alongside each module: `managed-cluster/tests/e2e/` contains scenario-based `main.test.bicep` files (automatic, azure, defaults, kubenet, priv, waf-aligned) with optional `dependencies.bicep` prerequisites; `aks-config-map/test/` and `aks-run-command/test/` provide `test.sh` harnesses that perform What-If validation followed by `az deployment group create` against a test resource group.
