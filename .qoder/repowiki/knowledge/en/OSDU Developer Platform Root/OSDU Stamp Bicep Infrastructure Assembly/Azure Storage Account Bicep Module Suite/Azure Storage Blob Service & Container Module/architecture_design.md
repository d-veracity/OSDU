Two-level Bicep module hierarchy under `bicep/modules/storage-account/blob-service/`. The root `main.bicep` declares the `Microsoft.Storage/storageAccounts/blobServices@2022-09-01` resource against an existing storage account (referenced via `existing = { name: storageAccountName }`) and configures blob service features such as versioning, soft delete, container soft delete, change feed, last access time tracking, restore policy, CORS, and default service version. It also emits diagnostic settings via a loop over `diagnosticSettings[]` using the shared `avm-common-types` type, and instantiates child modules for each container defined in the `containers` array. The `container/` sub-module provisions `Microsoft.Storage/storageAccounts/blobServices/containers@2022-09-01` resources scoped to the parent storage account/blob service, supports NFSv3 squash options, encryption scope defaults, public access levels, metadata, and optional immutable storage with versioning. A nested `immutability-policy/` sub-module is conditionally deployed when `immutabilityPolicyProperties` is non-empty. Role-based access control is handled by translating user-friendly role names through a local `builtInRoleNames` map into fully qualified role definition IDs before emitting `Microsoft.Authorization/roleAssignments@2022-04-01` on the container scope. Dependency direction is strictly top-down: root module → container module → immutability-policy module; no upward references exist.
