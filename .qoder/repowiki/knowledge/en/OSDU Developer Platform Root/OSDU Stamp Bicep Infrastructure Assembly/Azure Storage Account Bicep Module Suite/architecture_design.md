The root `main.bicep` instantiates the storage account resource and wires it to five sibling service modules — `blob-service`, `file-service`, `queue-service`, `table-service`, and `management-policy`/`local-user` — passing the same storage account reference so each child configures one protocol surface (blob/file/queue/table) independently. Each service module follows a uniform pattern: a top-level `main.bicep` enables the service and exposes parameters for diagnostics, then delegates named resources (containers, shares, queues, tables) to a nested sub-module under `<service>/<resource>/`. Cross-child consistency is enforced by shared parameter shapes (diagnostics, role assignments, encryption, private endpoints) consumed by every service module, while end-to-end scenarios in `tests/e2e/` exercise combinations of these children against real Azure deployments.
