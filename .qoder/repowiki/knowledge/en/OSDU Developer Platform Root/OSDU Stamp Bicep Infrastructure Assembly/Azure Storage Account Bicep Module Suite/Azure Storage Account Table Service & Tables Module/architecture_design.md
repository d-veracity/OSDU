Two-level Bicep module hierarchy under `bicep/modules/storage-account/table-service/`. The root `main.bicep` is the entry point: it declares a `Microsoft.Storage/storageAccounts/tableServices@2023-04-01` resource scoped to an existing storage account (referenced via `existing`), attaches zero or more `Microsoft.Insights/diagnosticSettings` resources driven by a `diagnosticSettings[]` parameter typed from `br/public:avm/utl/types/avm-common-types:0.2.1`, and iterates a `tables[]` parameter to deploy nested modules in `table/main.bicep`. Each child table module (`table/main.bicep`) creates a `Microsoft.Storage/storageAccounts/tableServices/tables@2023-04-01` resource on the parent's default table service and builds a `Microsoft.Authorization/roleAssignments@2022-04-01` collection for each entry in `roleAssignments`, resolving built-in role names to their GUIDs via a local `builtInRoleNames` map before emitting standard `name`/`resourceId`/`resourceGroupName` outputs. Dependency direction is strictly top-down: root module → child table module; both consume only remote AVM type references and existing storage accounts — no cross-references between sibling files.
