Two-level Bicep module hierarchy under `bicep/modules/storage-account/file-service/`. The root `main.bicep` declares the parent `Microsoft.Storage/storageAccounts/fileServices@2023-04-01` resource against an existing storage account (referenced via `existing`), applies protocol and soft-delete retention policy settings, creates zero-to-many `Microsoft.Insights/diagnosticSettings` scoped to the file service, and iterates over a `shares` array to deploy each share as a child module `share/main.bicep`. The `share/` sub-module defines `Microsoft.Storage/storageAccounts/fileServices/shares@2023-01-01`, resolves access tier defaults based on storage account kind, and conditionally deploys role assignments through a nested deployment module (`modules/nested_roleAssignment.bicep`) that loads `nested_inner_roleAssignment.json` and translates friendly role names to built-in role definition IDs. Dependency direction is strictly top-down: root module → `share/main.bicep` → `share/modules/*`; no upward references. Both modules expose uniform outputs (`name`, `resourceId`, `resourceGroupName`) and consume shared type definitions from the remote registry `br/public:avm/utl/types/avm-common-types:0.2.1` for diagnostic settings and role assignment schemas.
