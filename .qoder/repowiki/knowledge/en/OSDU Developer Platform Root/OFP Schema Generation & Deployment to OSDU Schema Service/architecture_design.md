Two-stage pipeline: a Python generator produces JSON Schema Service POST bodies, and a Bash script posts them in dependency order. `generate_schemas.py` reads the curated OFP entity set from `dVE/backend/src/adapters/ofp-schema-mapping.json` and property definitions from `openfootprint/standard/models/*.hck.json`, then emits one `<kindId>.json` per kind plus `schemas/manifest.json` listing reference-data before master-data for correct registration order. `generate_transaction_schemas.py` follows the same pattern but targets new `work-product-component--*` transactional entities (Emission Statement / Report families) with a hard-coded version of 1.0.0. The generated schemas are self-contained — system properties (`id`, `kind`, `version`, `acl`, `legal`, `tags`, timestamps) are inlined rather than `$ref`-ed — so first deploy avoids external resolution failures. `register_schemas.sh` is the deployment entry point; it parses `manifest.json` (and `manifest-transaction.json`) via embedded Python to deduplicate and order files, then POSTs each to `${OSDU_BASE}/api/schema-service/v1/schema` with `Authorization: Bearer <token>` and `data-partition-id`. Modes `test`, `refdata`, `transaction`, `all` gate which subset is posted, and the script stops on the first non-2xx response. All generated artifacts under `schemas/` are committed and treated as immutable inputs to deployment; regeneration requires the parent workspace sources.
